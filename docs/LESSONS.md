# Architectural Lessons Learned from the Legacy Bot

This document details the eight critical failure patterns identified in the production logs of the legacy downloader bot (`media-downloader-bot`), the defensive mechanisms implemented in `media-bot-v2` to prevent each issue, and the exact files and automated tests that verify each fix.

## Detailed Architectural Implementations

### 1. Capability Pre-Filtering, Host Parsing and Content-Type Validation
- **Problem in legacy bot:** The legacy bot treated `yt-dlp` as a catch-all sink. Non-media URLs such as `.zim` dumps or query-string mimics (`files.com?ref=youtube.com`) entered `yt-dlp`, consuming resources. HTML web pages were saved and charged as files.
- **v2 Solution:**
  - Strict host-only matching: all routing (`matches_youtube_url`, `matches_tiktok_url`, `router._host_matches`) parses `urlparse(url).netloc` and checks only host domain and subdomains.
  - `DirectEngine` and `download_provider_media` inspect `Content-Type` (HEAD and GET for direct links) and reject `text/*`, JSON and XML types. They also sniff the first 1KB of the body (`engines/content_check.py`): a BOM (UTF-8/16/32) is honoured, and bodies opening with `<!doctype`, `<html`, `<head`, `<body`, `<?xml`, `<!--`, `<script`, `<meta`, `<title`, or a JSON `{`/`[` are rejected with `NotMediaContentError` even when the server claims `application/octet-stream`. Rejected bodies are deleted. In the provider path this counts as that provider failing, so the next provider is tried. Known limit: a text file with no markup/JSON opener served as `application/octet-stream` is not detected.
  - Non-HTTP/HTTPS URI schemes (`ftp://`, `magnet:`, `torrent:`) are rejected at the gate.

### 2. Preflight Size Check via HEAD
- **Problem in legacy bot:** Large direct files were downloaded chunk by chunk before checking whether they complied with Telegram limits or bot storage limits.
- **v2 Solution:**
  - `DirectEngine` performs a `HEAD` request with timeout before opening a streaming `GET`.
  - If `Content-Length` exceeds `max_download_size`, `DownloadTooLargeError` is raised immediately.
  - The user receives an informative Hebrew message:
    `"⚠️ הקובץ גדול מדי (100.0GB). מגבלת ההורדה המרבית היא 4.0GB. טלגרם אינה תומכת בהעברת קבצים בגודל כזה."`
  - Zero bytes are written to disk and no fallback engines are called.

### 3. Single Attempt Per Provider / Route
- **Problem in legacy bot:** Duplicate retries of the same slow provider or local engine occurred sequentially, multiplying timeout delays.
- **v2 Solution:**
  - In `YouTubeEngine._try_fallback_providers` and `TikTokEngine.download`, an in-memory set `attempted_providers` records tried provider names.
  - At the route orchestration level `YouTubeEngine` and `InstagramEngine` both default to `max_retries = 0`: the local route is attempted at most once before falling back to providers.
  - Transport-level transient network errors (dropped chunks, connection resets) are handled strictly inside yt-dlp via `retries = fragment_retries = 3` (`TRANSPORT_RETRIES`), the same for YouTube, Instagram and TikTok-local.

### 4. Transparent User-Facing Attempt Summary (No Internal Leaks)
- **Problem in legacy bot:** When all fallback mechanisms failed, the user received an opaque error like "Download failed", or internal server paths (`/srv/media/tmp/abc123.part`) leaked to the UI.
- **v2 Solution:**
  - `RouteAttemptTracker` records each attempted provider/engine and a concise Hebrew reason for failure.
  - User-facing error text is a whitelist: the classifiers (YouTube, Instagram) map a raw error to one of a fixed set of Hebrew messages, or to a generic failure message; no fragment of the raw error is ever shown. Details are logged with `logger.warning` only. (M4.1 used a blacklist of leak patterns, which missed `.corp` hosts, API keys, JWTs and `HTTPSConnectionPool(host=...)`, and Instagram had no filter at all.)
  - `summarize_ytdlp_failure` inspects the original English error before translation (as well as translated Hebrew fallback) to correctly summarize failures like missing JS runtimes.

### 5. Accurate Diagnostics and Unified Sizing
- **Problem in legacy bot:** Format extraction failures were erroneously blamed on "outdated yt-dlp version", and size limits in YouTube surfaced raw English errors with incorrect byte numbers.
- **v2 Solution:**
  - `classify_youtube_error` accurately maps JavaScript runtime errors (Node.js/Deno missing for n-challenge decryption) to `texts.YOUTUBE_JS_RUNTIME_MISSING`.
  - Oversize enforcement lives in `DownloadGuard.check` (progress hook): it triggers on the declared total (`total_bytes`/estimate) or on the bytes received so far, whichever is larger, so a server that omits `Content-Length` is caught too. The message states the detected size (for an undeclared size, the amount received when the cap was crossed) and the configured limit. The cap applies per downloaded file/stream. In a playlist an oversize item is skipped and counted in the trim message; if every item is oversize the request fails with the size message.

### 6. Skipping Irrelevant Routes Without False Failures
- **Problem in legacy bot:** `gallery-dl` ran on URLs it had no extractor for, and `aria2` was reported as failed when the executable was absent from PATH.
- **v2 Solution:**
  - Providers verify `matches(url)` before fetch. Incompatible providers are skipped and logged at `INFO` level.
  - `ProviderHealthTracker.record_failure()` is only called when a capable provider actually encounters an error during execution.
  - Skipped providers are never included in the user-facing failure summary.

### 7. Explicit Item Count on Playlist Trimming & Incremental Split Uploads
- **Problem in legacy bot:** Trimming reasons were unstated or attributed exclusively to credit depletion even when items failed or were private; in multi-part uploads, if part 2 failed, the user was charged nothing and part 1 was lost.
- **v2 Solution:**
  - `YouTubeEngine` records `playlist_trimmed_reason` with counts, e.g. `"7 לא הורדו עקב מגבלת יתרת הקרדיטים, 1 אינם זמינים או נכשלו"` (never attempted because of the credit cap / over the size limit / failed).
  - **Credit model (volume, as in the legacy bot):** a credit is a unit of volume, not of requests or parts. One request costs `max(1, ceil(total_delivered_MB / MB_PER_CREDIT))`, computed by the single function `credits.service.credits_for_sizes` over the summed size of every part actually delivered. `MB_PER_CREDIT` is an env setting, default 200 (same as the old bot). Examples at 200: 1MB -> 1, 200MB -> 1, 200.1MB -> 2, 400MB -> 2, 1GB -> 6, 5GB -> 26; a 5GB file split into 3 parts still costs 26, and three 100MB parts cost 2. If only 2 of 3 parts are delivered, the request is charged for those two (the charge also runs on the error path); nothing delivered means nothing charged. Cache hits charge nothing. The remaining balance is shown on the `/settings` screen (read from the DB on each render), not in the file caption.
  - Caching is all-or-nothing: `pipeline.py` writes the archive cache entry only after every part was uploaded and forwarded to the archive, and never for a trimmed playlist. After a partial upload nothing is cached, so a repeat request downloads again instead of being served the delivered subset and told "done".

### 8. Total Request Time Budget, Separate Upload Timeout, and Active Thread Cancellation
- **Problem in legacy bot:** Requests had no overall time budget. In v2, coroutine cancellation via `asyncio.to_thread` did not kill running threads, allowing background byte transfers to continue consuming network bandwidth after cancellation.
- **v2 Solution:**
  - Independent budgets: `download_timeout` and `upload_timeout` (both defaulting to `request_timeout`) ensure heavy uploads are not starved by download duration.
  - Active cooperative cancellation: `CancellationToken` coordinates thread termination. In `DirectEngine` and provider downloader, `cancel_token.on_cancel(response.close)` immediately closes the underlying socket, breaking out of streaming loops, and the truncated file is deleted. In the yt-dlp engines the progress hook and a `match_filter` raise `DownloadCancelledSignal`, a subclass of yt-dlp's `DownloadCancelled`; unlike an ordinary exception, yt-dlp does not swallow it under a playlist's `ignoreerrors="only_download"`, so the whole playlist stops (verified against real yt-dlp: one GET after cancel, byte counter frozen). Every yt-dlp run then removes `.part`, `.part-FragN`, `.ytdl` and `.temp` leftovers on every exit path.
  - Distinguishing budget timeouts: only when the pipeline context manager actually expired (`cm.expired() == True`) is `texts.REQUEST_TIMEOUT_EXCEEDED` reported; foreign socket/HTTP `TimeoutError` exceptions report `texts.DOWNLOAD_FAILED`.
  - Verified by tests using simulated slow streaming sources with atomic byte counters showing byte transfer halts immediately upon cancellation.

### 9. A Video Telegram Accepts Is Not a Video Clients Can Play
- **Symptom:** Plus Messenger: "The application cannot play this video ... ERROR_CODE_IO_UNSPECIFIED". The upload succeeded and `supports_streaming`/`duration`/`width`/`height` were correct.
- **Root cause (verified with a real download):** the YouTube format selector ended in an unrestricted `bestvideo[height<=H]+bestaudio`, which yt-dlp resolves to AV1 (or VP9) + Opus and muxes into an `.mp4`. ffprobe of the delivered file: `av1` + `opus` in `mp4` (moov was already first, so faststart was not the cause). The old bot excluded `av01`/`vp09` for exactly this reason; v2 dropped that filter.
- **Fix:** (1) `build_format_selector` asks for H.264 (`vcodec^=avc`) and AAC (`acodec^=mp4a`) first; unrestricted codecs are only a last resort. (2) `upload/streamable.py::ensure_streamable` runs on every file that is sent as a video (any engine, incl. direct links and TikTok/Instagram): already H.264 8-bit 4:2:0 + AAC/MP3 in an MP4 with `moov` before `mdat` -> untouched; right codecs but wrong container / moov at the end -> `-c copy -movflags +faststart`; otherwise only the offending stream is re-encoded (libx264 veryfast / aac 128k). On failure the original is sent unchanged. "Send as file" mode never touches the bytes. (3) `probe` reports displayed (rotation-corrected) width/height.
- **Rule:** never judge "playable" by "Telegram accepted it". Check codecs, container and moov of the file that is actually uploaded (`tests/test_streamable.py` does, through the real pipeline).
